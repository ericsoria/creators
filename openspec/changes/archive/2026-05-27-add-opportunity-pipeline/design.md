## Context

The current backend supports internal authentication, taxonomy, brand and campaign catalogs, creator lead recruiting, approved creators, social accounts, and an API-driven operations UI. Campaigns and creators exist, but there is no first-class record for outreach attempts between them.

The MVP model identifies `Opportunity` as the pipeline stage between an approved `Creator` and a confirmed `Collaboration`. This change should model “we offered this campaign to this creator” without prematurely creating a collaboration. It should also preserve an event timeline so operators can see how an outreach thread evolved.

## Goals / Non-Goals

**Goals:**

- Add opportunities as the campaign-to-creator outreach pipeline.
- Add opportunity events as an auditable timeline of status changes, messages, replies, follow-ups, and notes.
- Keep API behavior consistent with existing `/api/v1` Laravel resource patterns: Sanctum auth, Form Requests, API Resources, pagination, validation errors, soft deletion, OpenAPI docs, and tests.
- Add an accept action that marks the opportunity accepted and establishes the future handoff point to collaborations.
- Keep controllers thin and put important state transitions in an action class.

**Non-Goals:**

- No confirmed collaboration model or collaboration execution pipeline in this change.
- No visit scheduling, publication tracking, creator scoring, or automation.
- No frontend Vue screens for opportunities in this change.
- No external messaging integration; events record operational history manually for now.

## Decisions

### Model opportunities as the outreach aggregate

`Opportunity` should belong to a `Campaign` and a `Creator`. It owns outreach-specific fields: status, channel, source account, message template, contact timestamps, follow-up count, rejection reason, notes, assigned user, and a nullable `converted_to_collaboration_id` reserved for the future collaboration handoff.

Alternative considered: adding outreach fields directly to campaign-creator pivot data. Rejected because outreach has identity, lifecycle, filtering, events, and future conversion behavior that deserve a first-class aggregate.

### Keep opportunity events append-only by default

`OpportunityEvent` should belong to an opportunity and optionally to the internal user who created it. Events should store type, old status, new status, message, metadata, and created_by. API support should focus on creating and listing events; updating/deleting events is not needed for the MVP unless tests reveal an operational need.

Alternative considered: only storing latest status/timestamps on the opportunity. Rejected because operators need outreach history, not just current state.

### Use explicit status transition actions for acceptance

The accept flow should use an `AcceptOpportunityAction` rather than putting transition logic directly in the controller. It should mark status as `accepted`, set response/contact fields if applicable, create an event, and remain idempotence-aware by rejecting already terminal or accepted opportunities.

Alternative considered: generic update endpoint can set status to accepted. Rejected as the only path because acceptance is a business transition and later must create a collaboration.

### Allow manual event creation

Operators should be able to append events such as `contacted`, `follow_up_sent`, `creator_replied`, `accepted`, `rejected`, `ghosted`, and `note`. Event creation may optionally update opportunity status when `new_status` is supplied, but the accept action remains the canonical acceptance flow.

Alternative considered: events only generated by system transitions. Rejected because early operations need low-friction manual logging.

### Prevent duplicate active opportunities per campaign and creator

The system should prevent creating multiple non-terminal opportunities for the same campaign and creator. Terminal statuses are `accepted`, `rejected`, `ghosted`, `expired`, and `cancelled`. This keeps active outreach queues clean while allowing future re-outreach if a previous opportunity ended.

Alternative considered: no uniqueness rule. Rejected because duplicate outreach records create operational confusion.

## Risks / Trade-offs

- Duplicate prevention with soft-deleted and terminal records can be subtle -> Mitigation: enforce through validation/query checks and tests rather than relying only on a simple unique index.
- Manual events can drift from opportunity status -> Mitigation: require valid statuses, record old/new status, and centralize status mutation when possible.
- Acceptance currently does not create collaborations -> Mitigation: reserve `converted_to_collaboration_id` and document that collaboration creation is a later change.
- Event metadata can become unstructured noise -> Mitigation: keep metadata optional and document expected event types in status-flow docs.

## Migration Plan

1. Add opportunities and opportunity events migrations with foreign keys, soft deletes where appropriate, and indexes for common filters.
2. Add models, relationships, factories, requests, resources, controllers, and action classes.
3. Add protected API routes and tests for authentication, CRUD, filters, event listing/creation, duplicate prevention, and acceptance.
4. Update OpenAPI and internal docs.
5. Run Laravel tests and Pint for touched PHP files.

Rollback is standard for additive migrations while no production data depends on the new tables.

## Open Questions

- Should `assigned_to` be required for operational ownership, or remain nullable for early MVP flexibility?
- Should event creation be allowed to mutate status immediately, or should only explicit action endpoints change status?
- Should accepted opportunities be allowed to remain without a collaboration until the next change, or should acceptance create a placeholder collaboration sooner?
